# Q1 grading: Staygreen architecture and the failed-check-to-email path

## Reference answer (from the code at e73a0df)

**Deployed parts**
- **Next.js app** (dashboard, REST at /api/v1, MCP at /mcp). It runs on Netlify with `@netlify/plugin-nextjs` and two POST rate-limit edge functions; any Node 22+ host also works. It is the only part holding the Supabase secret key. Evidence: `docs/deploying.md:13`, `netlify.toml`, `netlify/edge-functions/{member,public}-rate.ts`, `docs/architecture.md:48`.
- **Supabase Postgres**: schema, functions and restricted group roles (`probe`, `ingest`, `edge`, `alert_sender`, `watchdog`), applied with `supabase db push`. Evidence: `docs/deploying.md:14,61,65`.
- **Hosted services**: Clerk (sign-in, orgs, billing), Postmark (email) and Telegram (chat). Evidence: `docs/deploying.md:15,20-21`.
- **Probes**: systemd Node services on at least two Linux VMs, by default DigitalOcean `tor1`/`sfo3`, plus an optional Builder-only `fra1`. Peers talk signed HTTP on port 7070. Evidence: `docs/deploying.md:16,24`, `probe/main.ts:9-18`, `examples/probe/staygreen-probe.service`, `examples/probe/probe.env.example:30-35`.
- **Status edge**: Node renderer on 127.0.0.1:7080 behind Caddy, usually on a probe droplet, with Cloudflare proxying the status host. It polls and LISTENs on `status_edge_changed` and serves the widget `w.js`. Evidence: `edge/main.ts:55,73,88,90`, `docs/deploying.md:17,69`.
- **Ingest Worker**: Cloudflare Worker reaching the DB through Hyperdrive; it calls only `record_heartbeat`. Evidence: `ingest/src/index.ts:4-10,27`.
- **Sender Worker**: Cloudflare Worker with a `* * * * *` cron, plus a Telegram webhook at `/api/telegram/webhook`. It uses Hyperdrive and the `alert_sender` role. Evidence: `examples/sender/wrangler.toml:14-17`, `sender/worker.ts:35,67-77`, `20261023110000_alert_sender.sql`.
- **Watchdog Worker**: Cloudflare Worker with a minute cron and a SQLite Durable Object `Watchdog`. It may call only `watchdog_flush_status` and sends Telegram alerts to the operator. Evidence: `examples/watchdog/wrangler.toml`, `watchdog/worker.ts`.
- **CLI/stdio MCP package**: a client of the API only. Evidence: `docs/architecture.md:44`.
- **Direct calls between parts**: probe to probe, app to edge `/_edge/withdraw`, and Caddy to app `/api/edge/ask`. Evidence: `probe/peer.ts`, `src/lib/edge-control.ts:12`, `examples/edge/Caddyfile:7-9`.

**One failed HTTP check, probe to email**
1. **Check runs.** On the timer wheel, `tick` calls `checkAndReport`, which calls `runCheck`, which calls `checkHttp`. Evidence: `probe/runtime.ts:513-562,456-482`.
2. **Canary veto.** If the probe's own network looks isolated, the failure is dropped. Evidence: `probe/runtime.ts:499`, `probe/canary.ts:76-80`.
3. **Confirmation.** `needsConfirmation` sends the failure to `confirm()`. It asks each peer from `confirmersFor` in turn, with a signed POST /confirm, inside a 30 s total budget. The probe re-checks from itself after 20 s only if no other location is live or every peer declined (409). Otherwise, with no answer, the failure is unconfirmed. Evidence: `probe/state.ts:70-75`, `probe/runtime.ts:569-590`, `probe/peer.ts:109-120`.
4. **Routing to the home.** `deliver()` applies the outcome directly if this probe is the home (rank 0). Otherwise it goes to the outbox, which POSTs /report to the home once a second. Evidence: `probe/runtime.ts:605-638`.
5. **Home writes.** `Store.apply` runs: begin, `probe_lock_monitor`, version/order/duplicate fences, then `step()`. A `fail` verdict yields a transition to down, `open_incident` and `record_failure`. Then `probe_commit_monitor` runs. Evidence: `probe/store.ts:303-407`, `probe/state.ts:114-131`.
6. **Incident insert.** `probe_commit_monitor` (latest version) closes any stale open incident and inserts the incident titled "<name> is down". Evidence: `20261023100000_service_monitors.sql:123-187`.
7. **Outbox row.** In the same transaction, the AFTER INSERT trigger `incidents_alert_events` inserts an `alert_events` row of kind 'opened', unique per (incident, kind). Evidence: `20261022195510_alerts_email.sql:209-239,120`.
8. **Sender cron.** `runSender` reads `alert_pending_events`, reads Clerk members only if they are needed, and calls `alert_expand` (live version: `20261023120000_alert_channels.sql:132-201`, with routing). It then claims with `alert_claim_channels` under a 300 s lease, and `deliverEmail` calls `sendEmail` (Postmark), then `alert_mark`. Backoff runs 30 s to 1 h, with at most 8 attempts. An in-doubt claim is reconciled with `findSent` after the lease expires. Evidence: `src/lib/alerts/sender.ts:47-53,185-213,302,336-358,390-393`.
9. **Recovery.** Two passes take the monitor out of down and set `resolved_at`. The trigger then queues 'resolved' only if the monitor is up/degraded and an 'opened' event exists, and it goes only to the opened alert's recipients. Evidence: `service_monitors.sql:164-168`, `alerts_email.sql:224-231`, `alert_channels.sql:190-193`.
10. **Trap.** The `alerts_email.sql` header (lines 7-8 and 24-25) still says the sender is a Netlify scheduled function using the server key. That is stale.
